## 一、测试环境

- 硬件：ESP32-S3-DevKit（原生 USB，免驱）+ SHT30 模块（I2C 地址 0x44），面包板直连
- 固件：Arduino-ESP32 core 3.3.12，采集周期 2s，报文 `{"seq":N,"temp":x,"humi":y}`（QoS 0）
- 网络：被测 Wi-Fi CMCC（2.4G）；broker 为本地 mosquitto（Mac 192.168.1.5:1883）——**测试替身思想**：将不可控的公共 broker 替换为可控依赖，实现故障注入（kill broker=服务器宕机、断路由=网络断开）
- 观测工具三件套：IDE 串口监视器（设备视角）、消息日志器（时间戳+缺口标记，单实例+自动重连 v2）、Python 校验端（五层断言）

## 三、缺陷与发现

### Defect #1：网络恢复初期连接抖动（已确认，间歇性）

- **现象**：Wi-Fi 恢复后设备首次 MQTT 连接建立成功、上报 6 条（约 12s）后掉线，二次重连才稳定。日志双缺口铁证：78.2s（断网）+ 12.1s（抖动）
- **根因分析**：Wi-Fi 鉴权/信号未完全稳定时，上层抢建 MQTT 长连接，链路瞬断导致会话失效
- **严重度**：低（自愈，无人工干预），但真实可复现
- **改进建议**：首次连接建立后增加 N 秒连接健康观察期；或重连采用指数退避（当前固定 2s）

### 设计局限（非缺陷，量化确认）

- 断网期间消息无本地缓存、无补发：断 78 秒丢 25 条（人工期估算 39 条，自动断言修正为精确值）
- QoS 0 语义：无 broker 重投，"不重复"与"丢消息"是一体两面；如需至少一次语义需升级 QoS1 并处理消费端去重（幂等）

### 预期缺陷未复现（有效结论）

- 曾预判"固件缺 Wi-Fi 重连逻辑将永久失联"，实际 Wi-Fi 驱动默认自动重连兜底，设备自愈——测试报告中记录"已验证"同样是有效产出

## 四、自动化校验结果（消费端五层断言）

**基线窗口（180s 正常状态）**：接收 89 条；JSON 解析/结构/范围/重复 全 0 失败；丢消息 0；间隔均值 2.02s。

**断网复测窗口（300s，含 40s 断网）**：接收 60 条；格式类断言全绿；**seq 断档 1 处丢 25 条；重复 0 条**；间隔最大 223.9s。

校验维度与接口测试对应关系：JSON 可解析=响应完整性；结构断言=schema 校验；范围断言=边界值；seq 连续性=资金流水号对账；频率=响应时间断言。

## 五、测试过程事件与教训（方法论文献）

1. **观测事故**：双日志器实例导致消息成对"重复"，一度判为疑似设备缺陷——"先怀疑观测手段，再怀疑被测系统"的口诀实战验证
2. **观测链路可靠性**：初版日志器无自动重连，断网期自身掉线导致缺口数据被污染——观测链路可靠性必须 ≥ 被测系统
3. **面包板三大暗规则**（Day2 硬件排查五连案例）：列内导通/行内导通/中央凹槽断路——同列俯视对齐≠电气连通，压轴坑耗时最长
4. **自检指示灯法**：当串口观测不可靠时，给被测系统加 RGB 状态灯（红=失败/绿=通过）绕开观测通道，等价于服务的 health-check 端点

## 六、结论

被测链路在正常工况下数据完整、节奏稳定（T8）；故障注入场景下故障发现快（~6s）、恢复全自动（T1-T4、T9）；真实弱网环境行为符合典型覆盖边缘模式（T5）。发现 1 个低危真实缺陷（Defect#1，间歇性），确认 2 项设计局限并量化。整体质量可接受，建议按第三节改进方向演进。
